## الحكم التنفيذي

المشروع **ليس API مكتملة ولا جاهزة للإطلاق**. بُنيت خدمة Express/TypeScript مستقلة، ونواة Auth (login/refresh/logout)، وجداول Auth الخاصة، وRLS وصلاحيات تشغيل محدودة. استُكملت في هذه الجولة أدوات lint/format، واختبارات PostgreSQL محلية، وتطبيق مسار ترقية تدريجي من كلمة المرور القديمة إلى Argon2id لأول دخول صحيح. أُضيفت migration `alx_api_legacy_password_upgrade_0004_20261004` إلى Supabase، لكن **لم تُنقل أي كلمة مرور مستخدم حتى الآن**؛ جدول الاعتمادات ما زال صفراً.

لا يزال إطلاق Auth الحقيقي محجوباً بسبب نقص وظائف Auth/RBAC والتكاملات، وغياب اختبار شامل على DB منفصلة، ومفتاح JWT الخاص الذي سبق أن ظهر في تاريخ مستودع عام ولم يُدوّر في هذه الجولة. لم تُعد كتابة تاريخ Git بناءً على توجيه المستخدم. كلمة مرور `postgres`/مالك قاعدة البيانات لم تتغير.

## ما أُنجز في هذه الجولة

1. شُغّل تحقق محلي كامل: `check`, `lint`, `format:check`, فحوص تنسيق workflow، 10 حزم اختبارات وحدات/HTTP (46 اختباراً)، بناء الإنتاج، واختبار قاعدة PostgreSQL 16 محلية منفصلة.
2. أُضيف `scripts/test-db.ts` و`npm run test:db`؛ يرفض الاختبار أي مضيف/قاعدة غير محلية اسمها حرفياً `alx_api_test`، ويعيد إنشاء مخطط الاختبار، يطبق migrations، ويفحص RLS وgrants وreadiness ثم يجرب الدخول الوهمي وترقية كلمة مرور اصطناعية. لم تُستخدم بيانات المستخدمين في الاختبار.
3. حدّث CI ليستخدم PostgreSQL 16 مؤقتاً لكل تشغيل ويتحقق من lint وPrettier والوحدات ومهاجرات DB والبناء. نجح التشغيل الكامل للنسخة المرفوعة، بما في ذلك `npm run test:db`.
4. أُضيفت migration محلية `0004_legacy_password_upgrade.sql` وطُبقت على Supabase. دالتا `SECURITY DEFINER` تستخدمان `search_path=pg_catalog` ومالكهُما `postgres`؛ لا تعيدان كلمة المرور المخزنة، ولا يملك تنفيذَهما إلا `alx_api_runtime`. لا وصول مباشر للدور إلى `public.users`، ولا صلاحية لـ`anon` أو`authenticated`.
5. وسّع الكود `AuthService` وRepository لتثبيت كلمة المرور بـArgon2id عند أول تحقق ناجح من الاعتماد القديم. يُعاد التحقق داخل دالة DB قبل الإدراج لتقليل سباقات الدخول؛ إذا فشل التحقق فلا تُنشأ جلسة. لا يوجد مسار PIN. يحتفظ هذا التغيير بقيمة المصدر القديمة مؤقتاً لدعم العملاء القدامى إلى أن يُعتمد cutover، ولا يحذفها.
6. شُدد سابقاً تحقق توقيع Ed25519 لرفض الترميز غير canonical. نجح GitHub Actions للنسخة السابقة `f2c2818` (10 suites و44 اختباراً)، أما التشغيل الجديد فيشمل اختبار DB.
7. بعد موافقة المستخدم، ثُبتت كلمة مرور الدور `alx_api_runtime` الحالية في ملف `.env` المحلي فقط بصلاحية `0600`، وتأكد الاتصال؛ ستبقى كما هي حتى يعلن المستخدم اكتمال التطوير. لم تتغير كلمة مرور المالك ولم تُدوّر مفاتيح JWT. أزيل `.env` من النسخة الحالية/الفهرس وبقي مستبعداً من Git، لكن هذا لا يمحو التاريخ العام.

## تدقيق الاعتماد القديم — دون كشف قيم

أكدت مراجعة المصدر أن موصل النظام القديم يقارن مباشرة `row.password !== pass`، وأن PIN يُتحقق منه بمسار مستقل. لذلك يتعامل المسار القديم مع `public.users.password` كنص مطابق لكلمة المرور، ولا يستخدم PIN بديلاً لها.

أُجري فحص وصفي تجميعي فقط: 11 مستخدماً، لا توجد قيمة فارغة، ولا بادئات Argon2id/bcrypt/التنسيقات الشائعة المفحوصة؛ 5 أطوالها أقل من 20 حرفاً و6 بين 20 و39. هذه أعداد/نطاقات طول فقط؛ **لم تُقرأ أي كلمة مرور أو hash أو PIN أو معرّف مستخدم**. لم تُغيّر بيانات `public.users` أو `system_pin`. أظهر فحص metadata بعد migration أن عدد صفوف `alx_api_private.user_credentials` ما زال `0`.

## الحواجز الأمنية والتغييرات على قاعدة البيانات

- بقي دور `alx_api_runtime` غير مميز: `LOGIN=true` و`SUPERUSER/CREATEDB/CREATEROLE/BYPASSRLS=false`، ويملك schema usage وقراءة credentials المخزنة المطلوبة. كلمة مرور هذا الدور لم تُعدّل بعد المزامنة المعتمدة.
- migration 0004 لا تغيّر كلمات المرور ولا تحذف أعمدة أو صفوفاً؛ أنشأت فقط وظيفتي تحقق/إدراج مقيدتين. لم يُطبّق إدخال Argon2id على أي مستخدم، لأن ذلك يحدث عند أول تسجيل دخول ناجح عبر API بعد نشر الكود.
- جدول handoff المؤقت الذي استخدم لمزامنة كلمة runtime حُذف؛ التحقق الختامي أكد غيابه. لم تتغير كلمة مرور `postgres` أو المالك.
- ملف `.env` غير موجود في شجرة Git الحالية ومحمي من التتبع، لكن أسراراً قديمة ما زالت في تاريخ Git العام. المستخدم اختار عدم إعادة كتابة التاريخ/force-push؛ لذا تُعامل القيم التاريخية المنشورة كمكشوفة. مفتاح Ed25519 الخاص لم يُدوّر، ولذلك لا يستخدم النظام للإنتاج.
- فشل استعلام metadata أولي لأنه افترض وجود وظيفة 0004 قبل تطبيقها؛ لم يحدث منه أي تعديل. تلاه استعلام قراءة ناجح لخصائص الدور، ثم migration وقراءة تحقق ناجحتان.

## الخطوة التالية حسب ترتيب الخطة

بعد دمج الاختبارات محلياً، الخطوة الآمنة التالية هي إكمال Auth Core واختبار Repository/transactions والتدفقات الناقصة، ثم تثبيت RBAC؛ لا تبدأ وحدات Customers/Orders/Finance قبل قراراتها وقاموس البيانات. ينبغي لاحقاً نقل جميع العملاء من الوصول المباشر، وبعد cutover فقط اعتماد إزالة قيم المصدر القديمة من `public.users.password`. هذا التقرير لا يدّعي اكتمال API أو جاهزيتها للإنتاج.
