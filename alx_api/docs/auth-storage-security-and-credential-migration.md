# خطة حماية تخزين Auth وترحيل بيانات الاعتماد

**الحالة:** خطة محلية غير منفذة على قاعدة البيانات — 2026-10-04
**النطاق:** مراجعة تصميم `alx_api_private` واستراتيجية نقل الاعتمادات القديمة إلى Argon2id.
**قيد المستخدم:** لا SQL ولا DDL/DML ولا تغيير RLS/Grants في هذه المرحلة.

## الوضع المثبت

- الجداول المقترحة في `alx_api_private` غير منشورة بعد؛ الترحيل التجريبي السابق رُجع بالكامل عقب تحذير Supabase عن جداول بلا حماية RLS.
- لا يُفترض أن `DATABASE_SCHEMA.md` نسخة حيّة مطابقة؛ توجد فروق موثقة في `docs/pre-api/database-schema-verification-2026-10-04.md`.
- لم تُقرأ قيم `public.users.password` أو `public.users.system_pin` في هذه الجولة. لا يجوز اعتبار تنسيقها أو كونها plaintext/bcrypt/Argon2id أمراً محسوماً قبل تدقيق آمن للقيم الوصفية فقط.
- التنفيذ البرمجي الحالي يفصل Auth عن HTTP، ويحتفظ بالـrefresh token كـSHA-256 فقط، ويضيف Repository typed جاهزاً للاختبار. لا تُنشأ اتصالاته ولا تُفعل المسارات قبل اعتماد مخطط التخزين المحمي.

## خطة أمان مقترحة للجداول الخاصة

### قبل نشر أي جدول

1. **إخفاء المخطط عن واجهة Supabase Data API** وعدم إدراج `alx_api_private` ضمن exposed schemas؛ تعامل الخدمة معه عبر اتصال PostgreSQL مباشر فقط.
2. **فصل أدوار PostgreSQL:** مالك migration غير مستخدم وقت التشغيل، ودور runtime مخصص محدود بعمليات الجداول التي يحتاجها Auth، ودون صلاحيات إنشاء/تعديل مخططات أو قراءة جداول غير لازمة.
3. **منع الوصول العام افتراضياً:** لا تمنح `anon` أو `authenticated` أو `PUBLIC` وصولاً إلى المخطط أو الجداول؛ اختبر الرفض صراحةً قبل قبول النشر.
4. **تفعيل RLS وسياسة fail-closed** على كل جدول يحوي credentials أو جلسات أو أحداث، مع منع الوصول المباشر من العملاء. لا تُعامل RLS كبديل عن صلاحيات دور runtime أو فحوص Auth داخل التطبيق.
5. **مراجعة علاقات FK والفهارس والقيود** (تفرد hash، عمر/استخدام token، روابط user/session/family) بمقارنة snapshot حيّ، ثم مراجعة migration من شخص مخول قبل تطبيقها.
6. **اختبار سلبي قبل أي بيانات:** أدوار العميل لا ترى أي صف؛ دور migration وحده ينشئ البنية؛ دور runtime يستطيع فقط عمليات Auth الضرورية؛ لا توجد بيانات حساسة في logs أو responses.
7. **بوابة تمكين مستقلة:** لا يكفي وجود `DATABASE_URL` أو مفاتيح التوقيع لاعتبار الخدمة جاهزة. يجب التحقق من وجود المخطط والجداول المطلوبة، صلاحيات الاتصال، إعداد المفاتيح، credential migration، واختبارات smoke.

> جميع البنود أعلاه مقترح تحضيري. لم تُنفذ تعديلات RLS/Grants أو SQL في هذه المهمة التزاماً بنطاق المستخدم.

## استراتيجية ترحيل كلمات المرور القديمة

### التحضير

- حصر الاعتماديات عبر metadata/إحصاءات لا تكشف أي قيمة؛ لا تطبع كلمة مرور أو PIN أو hash في logs أو تقارير أو تذاكر.
- تصنيف التنسيقات داخلياً دون إظهار القيم. لا يُفترض أن عمود `password` يحمل plaintext أو خوارزمية بعينها.
- اعتماد مخزن credentials محمي ومهاجرة قابلة للإعادة، مع نسخ احتياطية مشفرة وسياسة تعافٍ/إعادة تعيين قبل التنفيذ.

### التعامل بحسب التنسيق

- **Plaintext مؤكّد:** تُجزّأ القيمة داخل عملية مهاجرة محدودة الوصول بـArgon2id وsalt فريد لكل مستخدم؛ لا تُكتب القيمة الأصلية في ملف أو log. تُدرج النتيجة في مخزن credentials ضمن معاملة لكل دفعة صغيرة، مع `ON CONFLICT`/سلوك idempotent معتمد في migration.
- **Argon2id صالح:** يُتحقق من التنسيق والمعلمات، ويُنقل hash كما هو فقط إذا كان متوافقاً مع السياسة المعتمدة؛ لا يعاد تجزئة hash بدلاً من كلمة المرور.
- **bcrypt أو تنسيق آخر:** لا يمكن تحويل hash إلى Argon2id مباشرة. إما مسار تحقق legacy مؤقت يعيد تجزئة كلمة المرور بعد نجاح دخول المستخدم، أو فرض إعادة تعيين كلمة المرور. يجب تحديد الخيار قبل migration.
- **قيمة فارغة أو تالفة أو ملتبسة:** لا تُستخدم للمصادقة؛ يفرض تعيين/إعادة تعيين كلمة مرور عبر مسار موثوق.
- **PIN:** لا يُرقّى إلى كلمة مرور ولا يستخدم كبديل عنها. إن بقيت الحاجة إلى PIN، يُصمم له نوع اعتماد منفصل ومحدود المحاولات، أو يُعطل حتى إعادة تعيينه. المخطط المحلي الحالي لا يعتمد PIN ككلمة مرور.

### التحقق والإغلاق

1. مقارنة **الأعداد فقط** قبل/بعد حسب فئة النتيجة (تم النقل، يتطلب reset، غير مدعوم)، دون أسماء أو قيم.
2. تحقق عينة اصطناعية في بيئة اختبار من نجاح Argon2id ومن فشل النص الأصلي/القيم الخاطئة، مع اختبار idempotence وعدم ازدواج user credential.
3. بعد موافقة منفصلة، إيقاف الاعتماد على الحقول القديمة وإزالة قيم المصدر وفق سياسة احتفاظ معتمدة؛ لا يُحذف المصدر قبل إثبات اكتمال النقل وخطة استرجاع آمنة.
4. فتح تسجيل الدخول الجديد فقط بعد نجاح فحوص المخطط والحماية والـrepositories وreadiness وsmoke.

## شروط تفعيل Repository الحالي

- اعتماد وتطبيق migration محمية للجداول التي يصفها `src/db/schema.ts`.
- اختبار Drizzle repository على قاعدة اختبار معزولة أو fixture معتمدة، ثم مراجعة transaction/lock behavior.
- توفير `DATABASE_URL` وEd25519 private key وhash Argon2id وهمي صالح عبر أسرار runtime، لا ملفات متعقبة.
- دمج composition root في `server.ts` بعد اجتياز شروط الأمان والجاهزية؛ حتى ذلك الحين تبقى `/api/v1/auth/*` على `503 AUTH_NOT_CONFIGURED`.

## قرار الجولة الحالية

تنفيذ محلي للكود والاختبارات والتوثيق فقط. **لا SQL، لا migrations، لا تغيير بيانات، لا تعديل RLS/Grants، ولا تفعيل Auth في server.**

الأقسام أعلاه تشرح التصميم قبل التنفيذ؛ بعد موافقة المستخدم نُفذت migration `alx_api_auth_rls_runtime_0003` على `alx_api_private` فقط. فُعّل وفرض RLS على الجداول الستة. سُحبت صلاحيات `PUBLIC`, `anon`, `authenticated`, `service_role`، وأنشئ دور `alx_api_runtime` بلا superuser/role-create/DB-create/BYPASSRLS. مُنح runtime أقل صلاحيات على الجداول المستخدمة فعلياً، ولم يحصل على أي امتياز على `password_reset_tokens` أو `auth_events` أو `public.users` مباشرة.

أضيفت `api_login_users` view كواجهة ضيقة للحقول `user_id, username, email, role, disabled` فقط. يستهلكها `DrizzleAuthRepository` بدلاً من قراءة جدول `public.users` مباشرة؛ لا تتضمن view كلمة المرور أو PIN. تم تفعيل login للدور ببيانات عشوائية محلية؛ الاختبار الفعلي عبر pooler نجح مع استعلامات صلاحيات محدودة. لم تُقرأ قيم `password/system_pin` ولم تُنقل؛ جدول `user_credentials` لا يزال فارغاً، و401 لهوية اصطناعية غير موجودة هو اختبار سلبي وليس دليلاً على نجاح مصادقة المستخدمين الحقيقيين.

تم توصيل factory والخادم محلياً، وأصبحت readiness تتحقق من أذونات Auth ذات الصلة. فحوص check/build و44 اختباراً ناجحة، واختبار HTTP أعاد readiness 200 وlogin اصطناعياً 401. لا يزال مسار credential migration شرطاً لتسجيل الدخول الفعلي.

**TLS:** تعذر التحقق من الشهادة دون CA المصدرة من لوحة Supabase. إعداد التطوير الحالي يستخدم TLS مشفراً لكن لا يتحقق من CA، وهو ليس إعداد إنتاج. تمنع validation اختيار production مع هذا الوضع؛ يجب ضبط `DATABASE_SSL_MODE=verify-full` و`DATABASE_SSL_CA_PEM` من مصدر CA الموثوق قبل النشر.

مراجع TLS الرسمية المستخدمة:
- [Supabase SSL enforcement](https://supabase.com/docs/guides/platform/ssl-enforcement): `require` يشفّر دون التحقق من CA/hostname؛ `verify-full` يتطلب CA من إعدادات قاعدة البيانات.
- [Supabase database connections](https://supabase.com/docs/guides/database/connecting-to-postgres): username للـshared pooler مخصص، وtransaction mode عبر port 6543، ويفضل TLS.
- [node-postgres SSL](https://node-postgres.com/features/ssl): خيارات `sslmode` في connection string قد تستبدل SSL object؛ الكود ينظفها ويحدد TLS صراحة.

أوصي بتدوير كلمة مرور مالك قاعدة البيانات التي أُرسلت في المحادثة. كما أن المستخدم أكد نشر `.env` الحاوي على سر runtime ومفتاح توقيع في repository عام؛ لا تضع هذه الأسرار في إعداد إنتاجي دائم، ودوّرها بعد التحقق/التسليم.
