# خطة الترحيل والتراجع — SwiftShip API

**التاريخ:** 2026-10-06 02:20 (+03:00)

## قاعدة التنفيذ

لا تُطبق أي migration على الإنتاج من داخل تشغيل التطبيق. تُراجع ملفات SQL، وتُطبق أولًا على PostgreSQL اختبارية، ثم تُؤخذ نسخة احتياطية، ثم تُطبق في خطوة نشر مستقلة مع تسجيل رقم migration والنتيجة.

## قبل التطبيق

1. تثبيت commit الإصدار ونسخة Node ونسخة PostgreSQL.
2. التحقق من `git diff --check` و`npm run check` و`npm run build` والاختبارات.
3. أخذ backup منطقي مشفر والتحقق من حجمه وhash ووقت إنشائه.
4. تسجيل أعداد الجداول الحساسة ومجاميع الحسابات المالية.
5. اختبار migration على نسخة staging مع smoke test.

## أثناء التطبيق

- تنفيذ migration واحدة في كل مرة.
- مراقبة زمن الأقفال وأخطاء الاتصال.
- عدم استخدام `drizzle push` أو `sync` على الإنتاج.
- إيقاف النشر فورًا عند اختلاف schema أو فشل constraint.

## التراجع

إذا فشلت migration قبل commit، تُترك المعاملة لتتراجع تلقائيًا. إذا كانت migration غير عكسية أو حدث فشل بعد commit، لا تُحذف البيانات يدويًا؛ يُعاد تشغيل الإصدار السابق مع migration تصحيحية معتمدة، أو تُستعاد نسخة backup بعد قرار حادث موثق.

## التحقق بعد التطبيق

يُعاد فحص صحة API، readiness، login، الصلاحيات، المسار المتأثر، أعداد السجلات، والمجاميع المالية. لا يُغلق fallback إلا بعد مقارنة النتائج بين المصدر القديم وAPI خلال نافذة مراقبة.

## الحالة الحالية

Migrations `0011_roles_api_runtime_write` و`0012_admin_password_reset` موثقتان ومطبقتان حسب سجل المشروع. ما زال اختبار backup/restore الكامل وrollback على بيئة PostgreSQL مستقلة بندًا متبقيًا قبل الإطلاق النهائي.
