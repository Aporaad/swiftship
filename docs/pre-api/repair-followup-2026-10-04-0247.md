## ما نُفّذ في هذه الدفعة

### 1. فصل شاشة الدخول عن واجهة البيانات القديمة

- أزيلت استيرادات `legacy-compat` واستعلامات البيانات المباشرة من `src/pages/Login.tsx`.
- نُقلت خطوات معالجة اسم المستخدم/البريد، تحميل ملف الحساب، رفض الحساب المعطل والمندوب، تهيئة الحساب الجذري المسموح به، والتحقق من PIN إلى `AuthGateway` وخدمة `staff-login.service.ts`.
- أصبح `Login` يستهلك ملف `AuthLoginProfileDto` آمناً لا يحتوي قيمة PIN، ويتعامل مع أخطاء `unknown`؛ لا توجد فيه مطابقة TypeScript AST من نوع `any` ولا import مباشر من `legacy-compat`.
- أضيفت اختبارات خدمة الدخول للبحث باسم المستخدم، إكمال الجلسة، الحساب المعطل/المندوب، ومسار PIN.
- **مهم:** لا تزال طبقة تنفيذ `CurrentSupabaseAuthGateway` تستدعي طبقة التوافق داخلياً. هذا ترحيل لحدود UI/Business Logic وليس إزالة نهائية لكل اعتماد على طبقة التوافق.

### 2. بدء وحدة مصادقة alx_api

- إضافة `argon2` واستخدام Argon2id وفق قيم الخطة الافتراضية: ذاكرة `65536 KiB`، تكلفة زمنية `3`، توازٍ `1`، وSalt عشوائي تشفيري مستقل بطول 16 بايت لكل hash.
- إضافة تحقق لحدود الموارد وإعدادات البيئة `ARGON2_MEMORY_KIB` و`ARGON2_TIME_COST` و`ARGON2_PARALLELISM`، دون تطبيق سياسة كلمة مرور غير معتمدة.
- إضافة Zod contracts لمدخلات login/refresh/logout.
- تسجيل المسارات `/api/v1/auth/login` و`/refresh` و`/logout` خلف منفذ `AuthUseCases` وRate Limit خاص (`AUTH_RATE_LIMIT_MAX=10`).
- لا توجد use cases/Repository موصولة في `server.ts`؛ الطلبات الصحيحة ترجع `503 AUTH_NOT_CONFIGURED` عمداً. لم يُفعّل اتصال قاعدة البيانات، وبقي فحص readiness غير جاهز افتراضياً.
- تحديث OpenAPI وREADME واختبارات HTTP لهذه الحدود.

## ما لم يُغلق بعد — لا يُعلن اكتمال خطة الإصلاح

1. ما زالت 91 ملفات مصدر تعتمد على `legacy-compat`؛ إزالة اعتماد شاشة Login وحدها لا تعني إتمام الترحيل. يجب ترحيل المستهلكين حسب المجال إلى Feature Gateways بعقود typed واختبارات لكل Query/Mutation/Subscription، ثم إزالة طبقة التوافق عندما يصبح عدد مستهلكيها صفراً.
2. ما زال 907 استخدامات `any` صريحة في كامل المصدر. النطاقات الحرجة المحددة أعلاه أصبحت خالية وفق AST، لكن التنظيف على بقية ملفات المصدر لم يكتمل.
3. Auth الحالي في النظام يقرأ `public.users` عبر الـadapter القديم، ويقارن `row.password` بالقيمة المقدمة مباشرةً. لذلك لا يجوز توصيل مسارات API الجديدة به أو إعادة استخدام كلمة المرور القديمة كنص صريح. الانتقال الفعلي يتطلب مخطط اعتماد آمن (`password_hash`)، مسار ترحيل/إعادة تعيين كلمات المرور، وجداول جلسات/Refresh Token وسياسة lockout.
4. لا يمكن تشغيل Auth API عملياً قبل اعتماد مخطط PostgreSQL وسياسة تحويل بيانات الاعتماد؛ هذه الدفعة التزمت بتوجيه «الشفرة وHTTP فقط، لا SQL/تغييرات DB». لذلك لا توجد migrations ولا اتصال إنتاج، وAuth endpoints تستجيب 503 عمداً.
5. لم يُستكمل بعد نقل جميع استدعاءات Portal إلى HTTP؛ فهذه الدفعة لا تغيّر مستودع Portal.

## قرار الحالة

تم **بدء** وحدة API/Auth آمنة من ناحية طبقة HTTP والتشفير، لكن ذلك ليس Auth API تشغيلية. لم تُغلق كل فجوات خطة الإصلاح، ولا تُعلن جاهزية إنتاجية أو إغلاق الخطة. تستلزم الخطوات التالية ترحيل بقية Feature Gateways على دفعات واختبار كل نطاق؛ أما ربط Auth بقاعدة البيانات فيحتاج قراراً منفصلاً يسمح بمخطط/ترحيل بيانات الاعتماد، وهو غير منفذ هنا.
