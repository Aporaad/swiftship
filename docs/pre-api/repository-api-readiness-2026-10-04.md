## 1. الحكم التنفيذي

**حالة تهيئة النظام: متقدمة برمجياً لكنها غير مكتملة للإعلان عن جاهزية إنتاجية.** توجد عقود وDTOs وData Gateways وحدود جلسة وصلاحيات، كما أن `server.ts` مفكك نسبياً ومسارات API Foundation للقراءة فقط موجودة ومسجلة. لكن قاعدة البيانات ما زالت وراء محول Supabase/Legacy، ولم يتحول `alx_api` إلى خدمة مستقلة؛ مجلده يحتوي حالياً على وثيقة الخطة فقط.

**القرار العملي:** يمكن الانتقال إلى إغلاق متطلبات المرحلة 0 وتجهيز Scaffold معزول وفق الخطة، مع عدم إطلاق Auth أو endpoints أعمال/مالية للإنتاج وعدم إجراء أي تغيير قاعدة بيانات قبل إغلاق بوابات جودة البيانات والـownership وHTTP/Portal والقرارات الأمنية. لا تعتبر نتائج الاختبارات المحلية وحدها موافقة على الجاهزية الإنتاجية.

## 3. مدى تنفيذ خطة إعادة الهيكلة قبل API

### ما أصبح موجوداً في الشفرة

- عقود Data Gateway متعددة المجالات، DTOs وMapper/Validation، Auth Session Provider، عقود Error/AsyncState، وصلاحيات UI.
- تقسيم الخادم إلى تطبيق/قاعدة بيانات/مسارات/Jobs/Proxy/Dev Server بدلاً من إبقاء كل شيء داخل `server.ts`.
- يوجد `server/routes/api-foundation.ts` ويُسجل من `server.ts`. يوفر عقداً versioned عبر `/api/v1/contract`، وقراءات محمية محلياً للمستخدم الحالي والعملاء والمناديب والطلبات والشحنات والمنتجات والحسابات والقيود المالية. هذه **قراءات فقط**، وتستعمل DbClient الحالي، وليست تنفيذ PostgreSQL/Drizzle مستقلاً داخل `alx_api`.
- اختبار `api-foundation.test.ts` يختبر DTOs وresponse/error envelope والصلاحيات وownership كدوال؛ لا يظهر فيه اختبار HTTP تكاملي للمسارات أو تحقق staging/E2E.

### ما بقي مفتوحاً وفق الفحص الحالي

- ما زال اعتماد النظام الفعلي على المحول قائماً: **91 ملفاً** داخل `src` تشير إلى `legacy-adapter` (147 سطر مرجع في نتائج البحث ضمن `src` و`server`). هذا لا ينفي وجود Gateway boundaries، لكنه يثبت أن cutover عن التنفيذ legacy لم يكتمل.
- ظهرت **34 مطابقة لـ`any`** في مسارات الحدود المفحوصة (`src/data` و`server/routes` و`src/api` و`alx_web/src/api` إن وجدت). يلزم تصنيفها وإثبات خلو العقود الجديدة منها.
- مراجعة AsyncState/Query/Mutation على كامل النظام، ونقل Portal فعلياً إلى HTTP، واختبارات staging/E2E والـrollback لا تزال بوابات مفتوحة في أحدث تقارير الخطة.
- `alx_web` ممثل في Gitlink عند `b7a9bb21210e81138549b4ef76329fbe5ea4dfff`، لكن مجلده فارغ في هذه النسخة ولا يوجد `.gitmodules`؛ لذلك لم يمكن تشغيل فحوص الموقع من هذا الـclone.
- تصميم API المستقل في خطته يستخدم Express 5 و`pg` وDrizzle وZod وArgon2id وJWT/RBAC، بينما API Foundation الحالي جزء من خادم النظام ويستعمل طبقة DB القديمة. يجب الفصل بينهما وعدم اعتبار الأساس الحالي بديلاً عن الخدمة المستقلة.

## 4. قاعدة البيانات: الحد الحالي للأدلة

لم أتمكن من إعادة الاتصال الحي في هذه الجلسة: إعدادا موصلي **Supabase** و**Supabase API** معطلان في إعدادات الجلسة، ولا توجد متغيرات اتصال قاعدة بيانات ظاهرة. لذلك ما يلي **نقلٌ عن آخر Snapshot محفوظ بالمستودع بتاريخ 2026-10-03، وليس نتيجة قراءة حية بتاريخ هذا التقرير**:

- 11 مستخدماً بقيمة `password` في `public.users`، و9 بقيمة `system_pin`.
- 5 قيود مالية غير متوازنة.
- جلستان بلا `expires_at`.
- مؤشرات ownership تاريخية غير متطابقة: 5/5 لقيم `orders.created_by` و`updated_by`، وقيم غير مطابقة في بعض سجلات `main_entry` و`account_trans`.
- ذكر التقرير أن RLS معطل على 50 جدولاً عاماً؛ لا يجوز تعميم أن الحالة ما زالت نفسها دون فحص جديد.

هذه عناصر Blocker/High موثقة تستلزم إعادة تحقق وخطة معالجة واعتماداً صريحاً. **لم ينفذ هذا التدقيق أي SQL أو DDL/DML أو Migration ولم يعدل قاعدة البيانات أو RLS/Grants.**

## 5. بوابات ما قبل البدء الإنتاجي

بحسب خطة `system_pre_api_restructure_plan_ar.md` وخطة الجاهزية المؤرخة 2026-10-03، لا يُعلن اكتمال الجاهزية قبل إثبات:

1. صحة بيانات حالية موثقة ومعالجة/قبول رسمي للـBlockers، مع ownership صحيح على بيانات ممثلة.
2. تحديد العقود والصلاحيات والـError/Response contract لكل مسار، ووجود تغطية route/integration/security.
3. نقل Portal إلى HTTP Gateway واختبارات staging/E2E؛ نجاح Boundary audit وحده لا يثبت اكتمال النقل.
4. حسم تدقيق `any` وAsyncState على النطاقات التي تحددها الخطة.
5. خطة تشغيل وrollback، وبيئة اختبار منفصلة عن الإنتاج؛ لا تُنفذ تغييرات بيانات أو مخطط ضمن هذه الخطوات.
6. حسم قرارات المرحلة 0 في خطة `alx_api`، خصوصاً نمط نقل Access Token، خوارزمية مفاتيح JWT، سياسة التخزين/التحديد الموزع، الأدوار والصلاحيات، استعادة كلمة المرور/MFA، CORS، الاحتفاظ بالتدقيق، المرفقات والبيئات.

## 6. ترتيب العمل المقترح من هذه النسخة

1. إتاحة موصل Supabase للقراءة فقط في الجلسة ثم إعادة Snapshot والتحقق من المخاطر على قاعدة البيانات؛ إلى حين ذلك تبقى أرقام 2026-10-03 تاريخية.
2. إعداد خطة remediation مكتوبة لكل Blocker حي، وعدم تعديل السجلات تلقائياً.
3. استكمال التدقيق المقاس للـlegacy boundaries و`any` وAsyncState، مع إعادة تشغيل اختبارات النطاق لكل دفعة.
4. توثيق/اختبار عقود Portal HTTP وownership وPublic Tracking دون PII على staging.
5. إغلاق قرارات المرحلة 0، ثم بدء المرحلة 1 بإنشاء Scaffold مستقل داخل `alx_api` (TypeScript strict، Express 5، validation/logging/error/request-id/health، CI واختبارات تأسيسية)، دون نقل Modules أعمال بعد.
6. إضافة PostgreSQL/Drizzle ومigrations أولية فقط إلى بيئة تطوير/اختبار مستقلة، بعد موافقة وخطة ترحيل؛ لا توصيل أول Scaffold مباشرة بقاعدة الإنتاج.
