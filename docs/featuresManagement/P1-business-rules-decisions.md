# P1 — سجل اعتماد قواعد الأعمال والقرارات العشرين

- **الإصدار:** P1.0
- **التاريخ والوقت:** 2026-10-20 03:51 (+03:00)
- **النموذج المنفذ:** Manus
- **المعتمد:** مالك المشروع عبر الأمر: «ابدأ بمراجعة وصياغة قواعد الأعمال والقرارات العشرين (المرحلة P1) الخاصة بالمسابقات والجوائز والكوبونات. واعتمادها»
- **الخطة المرجعية:** `خطة_تنفيذ_المسابقات_والجوائز_والكوبونات.md`، §§6، 13، 14
- **حالة السجل:** معتمد للإصدار الأول v1، ويُستخدم مصدرًا لقواعد الخدمات والعقود والاختبارات اللاحقة.

## نطاق الاعتماد

يحدد هذا السجل قواعد الإصدار الأول للمسابقات والجوائز وكوبونات العملاء. لا ينفذ SQL أو DDL، ولا يعتمد أسماء مفاتيح قاعدة البيانات الحية أو أرقام أدوارها. ستُراجع تلك التفاصيل قراءةً فقط في P2 قبل تصميم أي migration.

## الحالات والسياسات المقفلة

- تخزن الأوقات UTC، وتعرض المنطقة الزمنية في الواجهات.
- المشاركة تعتمد `customerId` المستنتج من جلسة البوابة، وليس أي معرف وارد من العميل.
- المعاينة ليست حجزًا، وإنشاء الطلب يعيد التحقق داخل المعاملة.
- لا تتغير سجلات الطلبات التاريخية ولا يعاد تفسير حقول كوبون الشراء الداخلي.
- الإلغاء أو السحب أو عكس الاسترداد لا يحذف التاريخ؛ كل إجراء حساس append-only وقابل للتدقيق.
- كل قائمة إدارية أو للعميل مصفحة ومحددة الأعمدة، ولا تكشف PII أو أسرار الأكواد دون حاجة وصلاحية.

## قرارات مؤجلة صراحةً إلى P2 دون تعطيل اعتماد P1

1. أسماء PK/FK الفعلية وعلاقة `portal_users` بـ`customers` و`orders`.
2. أرقام/معرفات أدوار RBAC الفعلية ومنح الصلاحيات لها.
3. حالة الطلب الموجودة فعليًا التي تمثل «القبول/الاعتماد» في قرار استهلاك الكوبون.
4. دقة العملة وتقريب خدمة الطلب الحالية، مع الالتزام بعدم إنشاء معيار موازٍ.
5. RLS وGRANTs ودور `alx_api_runtime` وسجل التدقيق/outbox الموجودين.

هذه ليست قواعد أعمال غير محسومة؛ هي تفاصيل تكامل يجب إثباتها قراءةً فقط من القاعدة والشيفرة قبل التصميم الفيزيائي.
