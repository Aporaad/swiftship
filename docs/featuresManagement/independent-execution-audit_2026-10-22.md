# تقرير التدقيق المستقل لتنفيذ `featuresManagement`

- **تاريخ التدقيق:** 2026-10-22، نحو 02:19 (+03:00)
- **طلب المراجعة:** تدقيق تنفيذ خطة المسابقات والجوائز والكوبونات المنفذ بواسطة Qoder، وتحليل الفجوات والأخطاء والمتبقي.
- **نطاق المراجعة:** جذر `SWIFTSHIP_SYSTEM`، و`alx_api`، و`alx_web`، ووثائق مراحل P0–P13، وفحص metadata حي لمشروع Supabase `ejrojwbbflzchasvgexr`.
- **طبيعة التدقيق:** قراءة ملفات المصدر/التوثيق وتشغيل فحوص واختبارات وقراءة metadata فقط؛ لم يُنفذ أي تعديل كود أو SQL/DDL/DML على قاعدة البيانات.

## الخلاصة التنفيذية

التنفيذ موجود فعليًا في المستودعات الثلاثة ويغطي شاشات إدارة المسابقات/الجوائز/الكوبونات، واجهات API، وصفحة العميل. لكن التنفيذ **غير جاهز للإطلاق أو الاستخدام العام**؛ إذ ظهرت مخاطر أمنية وتشغيلية مانعة، وبعض قواعد الأعمال المعتمدة في P1 لا يطابقها السلوك الفعلي.

أهم ثلاث نتائج مانعة:

1. جداول `feature_*` العشرة في `public` عليها `RLS=false`، ولدى دوري Supabase `anon` و`authenticated` صلاحيتا `SELECT` و`INSERT` المباشرتان عليها. هذا يتيح تجاوز حراس API عبر واجهة قاعدة البيانات المكشوفة، وقراءة/إضافة بيانات الميزات مباشرة.
2. دور `alx_api_runtime` لا يملك حتى `SELECT` أو `INSERT` أو `UPDATE` على تلك الجداول، وترحيل `0051_features_runtime_grants` غير موجود في سجل migrations الحي (آخر ترحيل ميزات هو `0050`). لذلك مسارات API التي تعتمد هذا الدور لا تملك الامتيازات اللازمة؛ وسجل المشروع نفسه سبق أن وثق أخطاء 42501/500 لهذه المسارات.
3. واجهة API لطلب العميل ما زالت تقبل `couponEnabled` و`couponRate` وتستخدمهما في التسعير عند عدم إرسال `couponCode`، مع أن قرار المالك وP1 يقصران هذين الحقلين على كوبون الشراء الداخلي في النظام الأساسي. هذا يترك خصمًا يتحكم بقيمته العميل عبر الطلب، ويمكن أن يصل الخصم إلى كامل مجموع المنتجات وفق حد التسعير.

**الحكم:** نجاح فحوص الأنواع ووجود واجهات لا يعني اكتمال الخطة. يجب إبقاء الميزة غير مفعلة/غير منشورة حتى إغلاق نتائج P0 الأمنية والمالية أدناه وإعادة التحقق على staging.

## نطاق الأدلة وحدودها

- تمت مراجعة ملفات التنفيذ ووثائق P0–P13، ومقارنة النتائج بقواعد الأعمال المعتمدة في `P1-business-rules-decisions.md`.
- اتصلت أداة Supabase بمشروع `ejrojwbbflzchasvgexr`. قُرئ سجل migrations وامتيازات/أعلام RLS metadata وتنبيهات الأمان فقط؛ لم تُقرأ صفوف العملاء أو الجوائز أو الاستردادات، ولم تُجر أي كتابة.
- أظهر `list_migrations` أن migrations الميزات `0048`, `0049`, `0050` موجودة في سجل القاعدة، بينما `0051_features_runtime_grants` غير موجود.
- نتيجة `get_advisors` ملتقطة عند `2026-10-21T23:18:29.811Z`، وتعدّ النتائج على مستوى المشروع كله، وليست خاصة بالميزة وحدها.
- كانت الفروع الثلاثة `main` وبحالة Git غير نظيفة وقت التدقيق (الجذر 42 مدخل حالة، وAPI 35، وWeb 8). لم أقم بإنشاء فرع/نسخة عمل، أو تبديل فرع، أو commit/stash، أو إعادة ملفات؛ يجب الحفاظ على تغييرات Qoder/المالك ومراجعتها قبل الدمج.

## النتائج مرتبة حسب الخطورة

### F-01 — حرج P0: جداول الميزات قابلة للوصول المباشر دون RLS

**الدليل الحي:** استعلام metadata شمل الجداول العشرة: `feature_contests`, `feature_prizes`, `feature_contest_prizes`, `feature_contest_entries`, `feature_draw_runs`, `feature_winner_awards`, `feature_coupon_rules`, `feature_coupon_issuances`, `feature_coupon_redemptions`, `feature_audit_events`. في كل صف: `rls_enabled=false` و`rls_forced=false`؛ كما كانت `anon_select=true`, `anon_insert=true`, `authenticated_select=true`, `authenticated_insert=true`. وبذلك لا تعتمد القراءة والإضافة على صلاحيات التطبيق أو حراس routes. تشمل البيانات المعرضة محتملًا رموز الإصدارات الشخصية، المشاركات، الفائزين، الاستردادات، وسجل التدقيق. لم أجر تجربة كتابة أو أقرأ محتوى الصفوف.

**الأثر:** تجاوز المصادقة وRBAC الخادمي مباشرة عبر PostgREST/واجهة Supabase، وقراءة أو إدخال بيانات الميزات من عميل عام. حصل فحص الأمان الحي أيضًا على `rls_disabled_in_public` بمستوى ERROR، وفيه جداول الميزات ضمن 63 جدولًا؛ و`policy_exists_rls_disabled` بمستوى ERROR لجداول عامة لديها سياسات لكنها غير مفعلة، على مستوى المشروع.

**المطلوب قبل الإطلاق:** ترحيل أمني معتمد يزيل امتيازات `anon` و`authenticated` المباشرة عن جداول الميزات ما لم تكن حاجة محددة، ويفعّل/يفرض RLS بسياسات مدروسة؛ ثم يمنح أقل امتياز لازم لدور API فقط ويتحقق من كل جدول. لا يُفترض أن إضافة `GRANT` لدور API تعالج كشف `anon`.

### F-02 — حرج P0: دور تشغيل API بلا امتيازات وترحيل 0051 غير مطبق

**الدليل الحي:** لكل الجداول العشرة كانت `runtime_select=false`, `runtime_insert=false`, `runtime_update=false` لدور `alx_api_runtime`. سجل migrations الحي ينتهي لميزة المسابقات عند `features_winners_coupons_0050`، ولا يحتوي `features_runtime_grants_0051`. ملف `alx_api/src/db/migrations/0051_features_runtime_grants.sql` موجود محليًا فقط، وسجل التشغيل المحلي يقول إنه بانتظار التطبيق؛ وتوثيق المتابعة يرصد مسبقًا 42501/500 عند اتصال الـ runtime.

**الأثر:** فشل عمليات القراءة والكتابة الإدارية عبر API حتى لو كانت صلاحيات المستخدم التطبيقية صحيحة. وجود ملف migration أو نجاح فحص TypeScript لا يثبت تطبيقه على القاعدة.

**المطلوب:** إعداد خطة منحة أقل صلاحية ومراجعتها مع معالجة F-01 في migration واحد أو تسلسل آمن؛ تطبيقها عبر مسار النشر المعتمد بعد الموافقة التشغيلية، ثم التحقق من سجل migration ومن `has_table_privilege` لكل عملية لازمة واختبار endpoints على staging. لا يكفي تشغيل 0051 بصورته الحالية إذا بقيت امتيازات anon/authenticated وغياب RLS.

### F-03 — حرج P0: بقاء حقول كوبون الشركة ضمن عقد إنشاء طلب العميل

**المراجع:** `alx_api/src/modules/portal/portal-owned.schemas.ts` (حول الأسطر 124–130)، و`portal-owned.service.ts` (حول 377–379، و601–625)، و`portal-order-pricing.ts`.

**الدليل:** مخطط طلب بوابة العميل يقبل `couponEnabled` و`couponRate`؛ ثم يمرر الخدمة هذين الحقلين لمحرك التسعير. عندما لا يرسل العميل كوبون `featuresManagement`، لا يوجد خصم خادمي بديل يمنع اعتماد الحقول القديمة. توثيق P13 يقول إن الخصم الخادمي يسبق حقول النظام الداخلي ولا يجمعهما، لكنه لا يزيل قبول هذه الحقول من عقد الطلب العام.

**الأثر:** يستطيع عميل تشكيل طلبه بقيمة `couponRate` غير خاضعة لمصدر كوبون موثوق. حتى لو لم تعرض `alx_web` الحقول في النموذج، يستطيع مستهلك API إرسالها مباشرة. يتعارض ذلك مع قرار المالك بأن هذه الحقول خاصة بكوبون الشركة الداخلي، ومع قرار P1 رقم 9 بعدم قبول `couponRate` من العميل.

**المطلوب:** فصل DTO/schema بوابة العميل عن DTO الطلب الداخلي، ورفض الحقول الإضافية صراحةً في quote وcreate، مع إبقاء حقول النظام الأساسي الداخلية على حالها. أضف اختبارات عقد سلبية تثبت رفضها ومنع تخفيض السعر بها، واختبارات انحدار تؤكد بقاء كوبون الشركة في مسار النظام الأساسي فقط.

### F-04 — عالٍ P1: معاملات PostgreSQL مبنية على استدعاءات `pool.query` المنفصلة

**المراجع:** `alx_api/src/modules/features-management/features-management.repository.ts`، مثل `transitionContest` (142–189)، `allocatePrize` (191–225)، `createEligibilitySnapshot` (280–315)، `assignWinners` (354–418)، `approveDrawRun` (419–465)، و`createCouponIssuance` (552–588).

**الدليل:** تبدأ الطرق المعاملة بـ`pool.query('BEGIN')` وتنفذ كل استعلام ثم `COMMIT`/`ROLLBACK` باستدعاء `pool.query` جديد بدل استئجار `PoolClient` واحد عبر `pool.connect()`. معاملات `pg.Pool` لا تضمن استعمال الاتصال نفسه في الاستدعاءات المنفصلة.

**الأثر:** في الضغط أو التوازي قد يقع `BEGIN`/القفل/التحديث/التدقيق على اتصالات مختلفة؛ فتضعف الذرية وحماية المخزون، وقد يحدث commit لجزء من العملية أو لا يحمي القفل التحديثات ذات الصلة. اختبارات mocks لا تثبت اتصال PostgreSQL فعليًا واحدًا.

**المطلوب:** تمرير `PoolClient` واحد لكل معاملة، واستخدام `try/finally` لضمان `release()`، وإجراء rollback آمن، ثم اختبارات integration على PostgreSQL تشمل سباق تخصيص آخر وحدة، إخفاق كتابة سجل التدقيق، وإعادة الطلب.

### F-05 — عالٍ P1: استهلاك الكوبون يحدث عند إنشاء الطلب لا عند قبوله

**المراجع:** `features-management.p9.ts` و`portal-owned.service.ts` (603–623).

**الدليل:** مسار الإنشاء يغيّر حالة الإصدار مباشرة إلى `redeemed`، ويرفع `usage_count`، ويسجل redemption بالحالة `redeemed` داخل معاملة إنشاء الطلب. قاعدة P1 رقم 11 تقرر الحجز عند إنشاء الطلب، والتحول إلى `redeemed` عند القبول/الاعتماد التشغيلي، مع التحرير مرة واحدة عند الإلغاء قبل الاستهلاك، وعكس خادمي idempotent بعده. لم يظهر في مسار الإنشاء/حالة الطلب ربط مكتمل يعيد الكوبون إلى حالة محجوزة أو يحرره عند رفض/إلغاء الطلب.

**الأثر:** الطلب المعلق أو الملغى قد يستهلك الكوبون نهائيًا، ويختلف الحد الفعلي للاستخدام عن السياسة المعتمدة.

**المطلوب:** إضافة دورة حالات واضحة ومقيدة (`reserved` → `redeemed` أو `released/reversed`) مرتبطة بمعاملة قبول/إلغاء الطلب الموجودة، مع قيود وتحديثات ذرية واختبارات فشل/تزامن/تكرار. اختبار quote/create وحده غير كافٍ.

### F-06 — عالٍ P1: لقطة الأهلية ليست مجموعة مجمدة قابلة لإعادة الإنتاج

**المراجع:** `features-management.repository.ts` (280–310، 354–390)، ولوحة `DrawWinnersPanel.tsx`.

**الدليل:** `createEligibilitySnapshot` يقرأ الصفوف المؤهلة الحالية ويخزن العدد وhash فقط في `feature_draw_runs`؛ لا يخزن عضوية اللقطة أو نسخة قابلة للتحقق منها. واجهة الفائزين تعيد تحميل المشاركات الحالية ذات `status='eligible'`، و`assignWinners` يتحقق من الحالة الحالية في `feature_contest_entries` وليس من عضوية snapshot. مراجعة المشاركة ما زالت تحدث الجدول الجاري.

**الأثر:** قد تتغير العضوية بعد التجميد، فلا يعود hash/العدد دليلًا كافيًا على أن الفائز اختير من المجموعة التي جُمّدت. يتعارض ذلك مع عدالة الاختيار والتدقيق وإمكانية إعادة البناء.

**المطلوب:** حفظ صفوف snapshot immutable ذات ترتيب/معرفات مشاركين، وربط اختيارات الفائزين بها، ومنع أو عزل أي تغيير أهلية لاحق عن النسخة المجمدة؛ واختبار التلاعب بعد التجميد واستعادة snapshot.

### F-07 — عالٍ P1: صلاحيات الواجهة غير مدرجة في كتالوج الأدوار، ومسارات API تستخدم صلاحيات أوسع

**الدليل:** `PERMISSION_NAMES.ts` يضيف 11 قيمة `features.*`، لكن `src/lib/permissions.ts`/كتالوج `PermissionDefinition` لا يعرّفها في `PermissionKey` أو كتالوج الأدوار. إعادة تشغيل `npm test -- --reporter=dot src/lib/permissions.test.ts` فشلت: الاختبار يطلب هذه المفاتيح الإحدى عشرة كلها ولا يجدها. كذلك route مراجعة المشاركة (`routes.ts` 350–354) وتجميد الأهلية (387–391) محروسان بـ`manageContests`، بدل الصلاحيتين المستقلتين `features.entries.review` و`features.draw.execute` المحددتين في P1. Routes القائمة لمراجعة المشاركات تستخدم إدارة المسابقات العامة أيضًا.

**الأثر:** لا يمكن ضمان إسناد الصلاحيات الجديدة عبر شاشة إدارة الأدوار في النظام الأساسي، كما أن الفصل الوظيفي المدون لا يطبق على الخادم.

**المطلوب:** مزامنة `PermissionKey` وكتالوج/واجهة إدارة الأدوار مع الصلاحيات الـ11، تعريف خريطة موحدة متوافقة بين مفاتيح core وAPI، استبدال كل route بالحارس الدقيق، واختبار وصول/رفض لكل دور. لا يُعتبر وجود `PERM` constants وحده إسناد RBAC مكتملًا.

### F-08 — عالٍ P1: مفتاح الميزة مفعّل افتراضيًا خلاف قرار الإطلاق المغلق

**المراجع:** `alx_api/src/config/env.ts:20–23` و`features-management.factory.ts:7–8`.

**الدليل:** `FEATURES_MANAGEMENT_ENABLED` له `.default('true')`، بينما P1 رقم 20 يقرر أن الميزة تبدأ مغلقة. لا يثبت ذلك قيمة إعداد البيئة المنشورة، لكنه يجعل التشغيل الافتراضي مفتوحًا عند غياب المتغير.

**المطلوب:** جعل الافتراضي fail-closed (`false`) واشتراط تفعيل صريح موثق بعد اجتياز بوابات قاعدة البيانات/الاختبارات وstaging، مع اختبار env فارغ في وضع الإنتاج.

### F-09 — متوسط P2: موافقة الشروط لا تسجل النسخة التي عرضت للعميل

**المراجع:** `features-management.schemas.ts:57–61` و`features-management.repository.ts:244–250`.

**الدليل:** الطلب يقبل `termsAccepted: true` فقط ولا يقبل `termsVersion`. الإدراج يأخذ `terms_version` الحالية من جدول المسابقة وقت الإرسال. إذا تغيرت الشروط بين تحميلها والضغط على المشاركة، فسيسجل النظام أن العميل وافق على النسخة الجديدة دون دليل أن تلك هي النسخة التي شاهدها.

**المطلوب:** إرجاع نسخة الشروط عند العرض، إرسالها كمعرف موافقة، ومقارنة النسخة المرسلة ذريًا بالنسخة الحالية عند التسجيل؛ ارفض المشاركة واطلب إعادة عرض/قبول النسخة الجديدة إذا تغيّرت. خزّن النسخة المقبولة ووقت القبول.

### F-10 — متوسط P2: حساب مهلة المطالبة يبدأ عند تعيين الفائز لا عند إشعاره

**المراجع:** `features-management.p7.ts:104–106` و`features-management.repository.ts:391–395, 431–452`.

**الدليل:** `claim_deadline` يحسب باستخدام `now()` عند إنشاء award وتعيين الفائز. الإشعار والحالة `notified` يحدثان لاحقًا عند اعتماد نتيجة السحب. P1 رقم 6 يربط الأيام السبعة بوقت إشعار الفوز الخادمي.

**الأثر:** تأخر الاعتماد أو الإشعار يقتطع من مهلة الفائز دون علمه.

**المطلوب:** ابدأ المهلة في معاملة الإشعار الفعلية، وخزّن وقت الإشعار، وضمّن شرط الموعد في تحديث المطالبة نفسه لتجنب سباق انتهاء المهلة بين القراءة والكتابة.

### F-11 — متوسط P2: إشعار الفوز لا يستخدم outbox/مفتاح تكرار مستقر

**المراجع:** `features-management.repository.ts:443–459`.

**الدليل:** إدراج `notifications` يحدث مباشرةً في المعاملة، مع منع تكرار يعتمد على وجود إشعار `features` للمستخدم في آخر دقيقة. لم يظهر سجل outbox مرتبط بمعرف award/حدث فريد؛ و`notification_ref` لا يُملأ في التحديث نفسه.

**الأثر:** قاعدة الدقيقة قد تمنع إشعارًا صحيحًا لحائز جائزتين/مسابقتين، ولا تعطي مفتاح idempotency ثابتًا لإعادة الإرسال. ومع مشكلة تثبيت PoolClient في F-04 لا يمكن اعتماد ذرية الإشعار والتدقيق.

**المطلوب:** outbox بمعرف حدث فريد لكل award/مستلم، ومعالجة retry/idempotency خارج معاملة إنشاء النتيجة، وتسجيل مرجع الإشعار النهائي.

### F-12 — متوسط P2: انتهاء/رفض الجائزة لا يحرر المخزون المحجوز

**المراجع:** تحديث الحالة في `features-management.repository.ts:499–524` وآلة انتقالات award في `features-management.p7.ts:62–75`.

**الدليل:** انتقال الجائزة إلى `expired` أو `rejected` يغير سجل award ويدقق الحدث، لكنه لا ينقص `quantity_awarded` أو `quantity_reserved` ولا يعيد الوحدة إلى المخزون. كما لا يظهر عامل مجدول لانتهاء الجوائز.

**الأثر:** تبقى وحدات انتهت مهلة المطالبة بها محجوزة ولا يمكن إعادة تخصيصها رغم أن P1 رقم 6 يطلب تحرير المخزون المتاح عند الانتهاء.

**المطلوب:** مهمة انتهاء موثوقة ومتكررة وآمنة، وإجراء transaction يعيد الوحدة مرة واحدة فقط مع سجل audit وقيود تمنع الرصيد السالب.

### F-13 — متوسط P2: إيقاف قاعدة كوبون يبطل الإصدار الشخصي السابق خلاف P1

**الدليل:** `calculateCouponDiscount` في `features-management.p7.ts:165–175` يرفض كل قاعدة ليست `active`. ويُمرر status القاعدة أيضًا عند التحقق من الأكواد الشخصية في `features-management.repository.ts`.

**الأثر:** تعطيل قاعدة كوبون يعطل التحقق من الإصدارات الشخصية السابقة، بينما P1 رقم 14 يقول إن الإصدارات الشخصية السابقة لا تبطل تلقائيًا عند تعطيل القاعدة، وتبقى حتى الانتهاء/السحب الفردي وفق السياسة المعتمدة.

**المطلوب:** افصل سياسة تحقق الرموز العامة عن الرموز الشخصية السابقة، مع حالات واضحة للإلغاء والانتهاء، واختبارات تنفي الإبطال الجماعي غير المقصود.

### F-14 — متوسط P2: مفاتيح idempotency لا تحقق إعادة النتيجة في بعض المسارات

**الدليل:** endpoint تعيين الفائزين يقبل `idempotencyKey` (`winnersAssignSchema` وواجهة core)، لكن `assignWinners` لا يربطه في سجل نتيجة/مفتاح request؛ إعادة الإرسال بعد انقطاع الاستجابة قد تُرفض بدل إرجاع النتيجة ذاتها. وفي تجميد الأهلية، `ON CONFLICT(idempotency_key)` يعيد السجل الموجود دون إثبات تطابق contest/payload، مع أن المفتاح فريد على مستوى القاعدة.

**المطلوب:** تخزين المفتاح مع actor/route/hash/نتيجة العملية، والتحقق من تطابق payload والكيان عند إعادة الاستخدام، وإرجاع الاستجابة السابقة نفسها؛ ارفض إعادة استخدام المفتاح لعملية مختلفة.

### F-15 — متوسط P2: قوائم «مشاركاتي/جوائزي/كوبوناتي» غير محددة بعدد الصفوف

**المراجع:** `features-management.repository.ts:340–345, 466–471, 589–595`.

**الدليل:** هذه الاستعلامات لا تحوي `LIMIT/OFFSET` أو cursor، بينما قوائم الإدارة تستخدم pagination.

**الأثر:** زيادة عدد سجلات العميل يرفع حجم رد API ووقت تحميل صفحة الهدايا بلا حد.

**المطلوب:** pagination ثابتة/محددة مع عقود وبوابة عرض واختبارات للـ maximum page size.

### F-16 — ملاحظة أمان على مستوى المشروع: التنبيهات الحية تتجاوز جداول الميزة

`get_advisors` أظهر `rls_disabled_in_public` بمستوى ERROR على 63 جدولًا، و`policy_exists_rls_disabled` على 20 جدولًا، و45 دالة `SECURITY DEFINER` قابلة للتنفيذ من `anon`. بعض الأسماء تشمل جداول أعمال/موظفين وعمليات مالية، لذا يلزم مسار معالجة أمني مستقل على مستوى المنصة؛ لا يُنسب كل ذلك إلى تنفيذ Qoder لهذه الميزة. روابط المراجع: [RLS Disabled in Public](https://supabase.com/docs/guides/database/database-linter?lint=0013_rls_disabled_in_public)، [Policy Exists RLS Disabled](https://supabase.com/docs/guides/database/database-linter?lint=0007_policy_exists_rls_disabled)، [Public Can Execute SECURITY DEFINER Function](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable).

## التحقق والاختبارات

- فحوص `npm run check` السابقة على الجذر و`alx_api` و`alx_web` انتهت دون إخفاق TypeScript في هذه الجولة.
- اختبار النظام الأساسي المحدد `npm test -- --reporter=dot src/lib/permissions.test.ts`: **فشل** — `permission catalog contract`؛ القيم الإحدى عشرة `features.*` متوقعة في سجل الصلاحيات الموحد لكنها مفقودة من كتالوج الأدوار.
- تشغيل Jest الكامل لـ`alx_api`: سجل التدقيق المحلي عرض 538 اختبارًا ناجحًا، وفشل تشغيل suite واحدة بسبب `ENOSPC` عند كتابة Jest cache، لا بسبب assertion. أُعيد تشغيل suite المتأثرة `tests/portal-owned.repository.search.test.ts` بـ`--no-cache` ونجح الاختبار (1/1). يجب إعادة المجموعة الكاملة على بيئة مستقرة وتسجيل نتيجة خضراء متصلة قبل الإطلاق.
- تشغيل `alx_web` tests السابق لم يسجل إخفاقًا في الطرفية، لكن يلزم smoke/e2e متصل مع API/DB بعد إصلاح 0051 وRLS.
- فحوص الأنواع/اختبارات الوحدات لا تثبت أن migrations مفعّلة أو أن الأدوار والامتيازات الفعلية صحيحة؛ الدليل الحي هنا مستقل عنها.

## خطة الإغلاق المقترحة — بالترتيب

### Gate 0 — احتواء قبل أي نشر (P0)

1. إبقاء `FEATURES_MANAGEMENT_ENABLED=false` صراحةً في كل بيئة إلى حين الإغلاق، وعدم تعريض الواجهة العامة/إدارة النظام عبر قاعدة البيانات.
2. إغلاق وصول `anon` و`authenticated` المباشر عن جداول الميزات، وتفعيل RLS والسياسات مع منح أقل صلاحية لدور API. راجع استشاري الأمن وصاحب قاعدة البيانات قبل تطبيق migration؛ هذا التقرير لم يغيّرها.
3. إكمال 0051 أو migration بديل آمن ومنح `alx_api_runtime` العمليات اللازمة. ثم اختبر role privileges وDB connection الفعلي قبل إعادة تجربة routes.
4. تقييم تعرض محتوى الميزات/رموز الكوبونات حتى وقت الاحتواء من خلال سجلات الوصول المتاحة؛ لا تسحب أو تدوّر بيانات حية قبل تقدير الأثر وخطة متفق عليها.

### Gate 1 — صحة الخصم ودورة حياة الاسترداد (P0/P1)

1. أزل `couponEnabled/couponRate` من schemas الخاصة بطلبات العميل والـ quote، ولا تمررهما من بوابة العميل؛ أبقِ الحقول الداخلية في نموذج النظام الأساسي.
2. ثبّت دورة reserve → redeem عند الحالة التشغيلية المعتمدة → release/reverse مرة واحدة عند الفشل/الإلغاء، داخل transaction موحدة تشمل order/redemption/usage.
3. استبدل المعاملات متعددة `pool.query` بـ`PoolClient` واحد، واختبر سباقات آخر استخدام والمخزون وتراجع audit.

### Gate 2 — العدالة والتدقيق والتفويض (P1/P2)

1. خزّن snapshot immutable للمشاركات المؤهلة واربط كل فائز بها؛ لا تسمح باستخدام القائمة الحالية بعد التجميد.
2. أكمل قاموس permissions في النظام الأساسي وطبّق الحراس الدقيقة في API لكل route، ثم أصلح اختبار `permissions.test.ts`.
3. اربط موافقة المستخدم بنسخة الشروط المعروضة، وابدأ مهلة المطالبة من الإشعار الفعلي، وأضف تحرير المخزون عند انتهاء/رفض جائزة.
4. استخدم outbox ومفاتيح أحداث مستقرة للإشعارات، وأكمل idempotency القابلة لإرجاع النتيجة نفسها، وأضف pagination لقوائم العميل.
5. طبّق سياسة P1 للإصدارات الشخصية بعد تعطيل قاعدة الكوبون.

### Gate 3 — قبول الإطلاق (P1–P13)

- Migration dry-run/review، ثم تطبيق migrations المصرح بها وتوثيق hashes/أرقامها في DB logs.
- Integration tests مع PostgreSQL حقيقي ودور runtime، مع التوازي والrollback؛ اختبارات API authorization (مسموح/مرفوض)، وAPI customer isolation، وe2e على `alx_web`.
- مراجعة مستشار Supabase بلا أخطاء أمنية مرتبطة بجداول الميزات، smoke test لإنشاء مسابقة، مشاركة، لقطة، اعتماد، مطالبة، coupon quote، إنشاء طلب، إلغاء/تحرير، ثم اختبار إيقاف الكتابة.
- مراجعة إعدادات production صراحةً، خطة مراقبة/تنبيه/rollback، وتوثيق مالك التشغيل قبل تفعيل المفتاح.
- بعد اجتياز البوابات، إعادة تشغيل جميع الفحوص وتوثيق نتائجها، ومراجعة diffs وحالة Git دون فقد أي تغييرات قائمة. لم أنفذ merge أو commit.
